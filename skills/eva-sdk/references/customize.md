# 定制 Eva SDK 应用

## 目标

在已验证的 example 或用户项目上修改已发布 SDK 的公开能力与应用层行为，不依赖特定语言、平台或内部实现。

## 执行

1. 明确目标行为、保持不变的行为、完成条件和不可接受失败。定位当前可工作基线；没有基线且改动依赖 runtime 效果时，先执行 `run-demo`。
2. 从目标项目已安装依赖匹配 `sdk-catalog.json`；默认使用当前解析版本的发布物公共契约，不要求先读取或运行 example。只有用户明确选择 Demo 基线时，再读取固定 example 及其版本。
3. 按优先级确认可用公共面：目标项目现有用法、当前版本发布物声明的公共入口与契约、SDK catalog 官方文档，以及用户明确选择时的固定 example。不要用模型记忆补名称、类型或签名。
4. 先把需求归入职责，不预设某个 SDK 当前一定提供哪些具体选项：
   - 构造与公开配置；
   - 生命周期、控制和资源释放；
   - 输入、输出与可观察状态；
   - 宿主应用的 UI、交互和编排；
   - 发布物明确声明的正式扩展点。
5. 建立“用户目标 -> 公共契约 -> 目标文件/配置 -> 验证传感器”的映射，再做最小 patch。不要顺带升级 SDK、重构无关模块或更换宿主技术栈。
6. 使用当前生态和平台的原生 checker，按配置/schema、编译或静态检查、lint、针对性测试、release 构建、runtime 的顺序验证。验证粒度要小于改动粒度，并覆盖相关生命周期与资源释放。
7. 回看预期：列出哪些效果已由自动传感器证明、哪些需要用户在真实凭证、网络、权限和目标设备/运行环境中体验。没有真实操作证据时不声明 L3。

## Fail closed

- 发布物公共契约中不存在所需能力：说明缺口，不进入 internal runtime、transport 或测试 seam。
- 用户选择的 Demo 与目标项目 SDK 版本不同：不静默升级/降级；先让用户选择基线。直接定制已有项目时默认保留当前版本。
- 修改需要新的生产凭证分发、后端服务或权限模型：将其作为单独架构决策，不从本地 key-file 流程外推。
- 运行失败且官方 example 也失败：先处理工具链、发布物、Gateway 或目标环境问题，不以大规模应用改写掩盖基线故障。
